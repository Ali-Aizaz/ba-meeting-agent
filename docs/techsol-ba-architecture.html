What may leave the meeting & domain guardrails

The BA Assistant is strictly scoped to car/automotive questions and meeting notes/tasks. Any unrelated question (weather, crypto, general trivia, coding, cooking) is blocked locally by _is_off_topic before reaching the LLM or web search. Public car pages are fetched only when has_car_topic(query) is true, and query_allowed / strip_meeting_text guarantee that meeting transcripts, participant names, timestamps, and Notion/Meet URLs never enter a web search query.

How one meeting runs

The adapter joins, posts consent, and turns captions on. Caption lines accumulate with speaker and meeting time.

“Hey BA” starts the addressed loop. Anything else stays quiet, except a complete overheard task, which is written and confirmed.

Save runs when asked and when the meeting ends. The bot leaves one minute after it is the last one in the call.

Meet adapter

Chromium runs headed under Xvfb on the cloud server, one meeting at a time. It joins Google Meet as TechSol BA (a saved sign-in, or a guest the host admits), with the mic and camera off. Incoming participant video is rejected at the WebRTC SDP level (a=inactive) and via Meet’s audio-only receive setting so 0.5-vCPU containers spend zero CPU decoding video streams. The first chat line is the consent notice. It turns captions on, leaves one minute after it is alone, and saves before it goes. Chat DOM interactions are serialized with an async lock (_ui_lock) and use fast bulk text insertion (fill / insert_text). Chat posts are allowed only for consent, a reply, a task confirmation, or the saved-notes link.

Google Meet

The only platform this build joins. Live captions are Meet’s own speech-to-text, drawn in the page for the participant who turns them on. There is no separate caption API. Chat is plain text. Zoom and Teams stay on the diagram as a second adapter.

Caption line

A script watches the captions region and commits a line when the text settles, the speaker changes, or a new row replaces it. Speaker aliases are applied, then the line is stored. The clock is time since the bot was admitted. Captions are strongest in English, and the page structure can change. If they never appear, typed “Hey BA” still works. No second speech-to-text service is added.

Chat message

Read from the same page. The bot’s own messages are ignored. A typed “Hey BA” is a trigger even when captions are empty, and it is how someone asks the bot to save or to leave.

Wake phrase

Accepts “hey ba”, “hey bea”, “hi ba”, “okay ba”, and “ok ba”. Rejects lookalikes such as “hey bob”, “bay area”, and “the BA team”. The question is the words after the phrase. If the phrase arrives alone, it waits a few seconds for the same speaker, then asks one short clarifying question. A follow-up to that question does not need a second “Hey BA”. Ordinary talk produces no trigger.

Scope & topic gate

First guardrail layer after a “Hey BA” wake phrase (policy.py & loop.py). Classifies every question into one of three paths: (1) Car/automotive question (is_car_question / has_car_topic or a local knowledge-base hit in data/knowledge/*.md), (2) Meeting, task, or database question (is_meeting_question or keyword overlap with the live digest / stored Notion & SQLite records), or (3) Off-topic refusal (_is_off_topic). If a question is neither about cars nor about the meeting/tasks, the agent immediately replies with OFF_TOPIC (“I can only help with car and automotive questions or this meeting’s notes and tasks.”) without calling the LLM or web search.

Agent loop

Runs only after a wake phrase and the scope gate, dispatched through a non-blocking asyncio.Queue worker (replies()) so 300ms caption and chat polling never stalls. The prompt wraps untrusted context in XML delimiters (<meeting_digest>, <knowledge>, <web_results>, <question>) and enforces the persona rule to answer only car/automotive or meeting/task questions. For a car question it calls search_knowledge first, then search_cars when local coverage is weak or current specs/prices/models are requested (should_search_web). For meeting/database questions it merges the live digest with stored Notion tasks/summaries and SQLite history via fetch_db_context.

Knowledge base

Curated automotive Markdown files under data/knowledge/ (hybrid, EV battery, chassis, safety, and sourced examples). KnowledgeIndex.search normalizes automotive stems (e.g., braking → brake, charging → charge), includes file-stem tokens, and boosts heading/multi-token matches so natural-language car questions score accurately.

Search & citation guardrails

Enforces both outbound search safety (guardrails/search.py) and outbound chat citation integrity (guardrails/citations.py): (1) Car-only search enforcement: query_allowed, OpenAIResponsesClient.search_cars, and tool dispatch all require has_car_topic(query) == True, blocking any non-car web search. (2) Meeting privacy scrub: query_allowed and strip_meeting_text reject or strip non-addressed caption snippets (≥12 chars), participant names (while preserving car brands and ignoring generic labels like “Unknown speaker” or “You”), timestamps, and Notion/Meet URLs. (3) Source citation gate: reply_status and finalize_reply require every car reply with numbers/prices/units to cite (src: filename.md) or an https:// URL; uncited drafts are regenerated once, then replaced with NOT_SURE.

Chat reply

One reply per trigger, after the guardrails pass. Meet chat does not render Markdown, so the answer is a few sentences or a small plain-text table. A save posts the Notion URL with reason MEETING_SAVED when people are still in the call.

Task extractor

Runs on recent caption lines in the background and does not wait on a reply. Queued lines are drained in batches and checked against a deterministic local task-signal pre-filter (might_contain_task) so casual non-task speech skips the LLM call entirely. When triggered (optionally routed to llm.task_model), the model returns JSON: task, owner, due date, and who said it, with web search off. A question to the bot is not a task. An overheard task missing an owner or a due date is dropped without interrupting the meeting. A complete task calls create_task backed by an in-memory Notion deduplication cache (_task_cache).

Confirmation

A new row is confirmed in chat, for example “Task added: Ali — cost sheet — Fri”. If that task and owner already exist, including from an earlier meeting, the chat says it is already tracked and nothing is written again. A failed write is also said in chat.

Meeting memory

Stores caption lines, tasks, and posted bot replies (add_reply / recent_replies(limit=5)) in SQLite with WAL mode and canonical Meet URL matching (_canonical_url) so a restart or URL variant resumes cleanly. digest() provides live meeting participants, tasks, recent bot replies, and recent captions, while stored_context() / all_tasks() surface tasks and captions stored across earlier meetings in SQLite.

save_meeting

Triggered by “Hey BA, save the meeting”, and by the adapter when the meeting ends or someone tells the bot it can go. The empty summary page is created at join (ensure_summary_page) so the consent message can include a real link. When saved, properties (summary paragraph with web search off, plus the task list) are updated via PATCH /pages/{id}, and the collapsed transcript toggle block is appended once via PATCH /blocks/{id}/children. Running save twice updates the same page idempotently.

OpenAI

Default client is the OpenAI Responses API with automatic model fallback to gpt-4o-mini if a configured preview model is unavailable, plus deterministic local fallback in AgentLoop._fallback_answer if the API key fails. Web search is enabled only inside search_cars for verified car queries.

Public web

Restricted strictly to car/automotive queries (has_car_topic(query) == True). Primary search uses OpenAI web_search; if the OpenAI API fails or returns empty, _public_web_search falls back to DuckDuckGo HTML and Wikipedia API search with source URLs. Meeting transcripts, participant names, and Notion URLs are stripped/blocked before any request leaves the server.

Notion

Reads and writes two Notion databases configured via notion_schema.yaml: tasks_db and summary_db. At runtime, list_tasks, list_summaries, and database_context fetch stored tasks (owner, due date, status, speaker) and past meeting summaries/transcripts (cached for 30s) so “Hey BA” can answer questions about existing tasks and past meetings as well as create deduplicated tasks and save meeting notes.

Second platform

The same MeetingPlatform interface, with another adapter. Meet captions do not transfer, so that platform would need its own transcript source. This build joins Google Meet only.

Voice reply

The chat reply would stay. A short spoken version would use a text-to-speech API on the provided key, such as OpenAI speech. The mic would turn on only while the bot speaks. Today the mic stays off and every answer is typed.

Decisions, Requirements, Risks

Three more databases linked to the meeting summary. In this build those topics are mentioned inside the summary when they came up. They are not their own rows.

BOM and compare

build_bom would return part, quantity, cost, and supplier. compare would return a short trade-off. Both would read the same knowledge base and would still not send the transcript out. Neither tool exists in this build.

Past meetings

When someone asks about a previous meeting, read older summaries and open tasks from Notion. Today the memory used in a reply is this meeting only. Dedup against tasks already stored from earlier meetings still happens at write time.

Data-flow rule

The knowledge base is ours. The internet is used to fetch public car pages in. search_cars is rejected when the query contains a caption line, a participant list, or a Notion URL. The digest may still be sent to the LLM for a reply. It is not copied into the search query.
